# 第二语言：全量永久保存、容量冗余与零持续账单研究

日期：2026-10-05，北京时间。研究产物；本轮没有迁移数据、开通付费服务或改变正式学习协议。

本文更新此前《永久保存与分层存储》的容量结论及平台选择。用户明确希望停止产出后不必继续为静态存量付费，因此“HF 不够就自动转为 R2/B2 付费全量保存”不再是默认终态。

用户后续明确：优先国际可靠大牌，不采用国内品牌作为存储基座。本报告据此调整推荐；123 等国内容量信息仅保留为研究记录，不计入最终推荐容量池。

## 1. 已确认的使用量与结论

- 全部约 15,000–16,000 个主词，按每日 40 主词估算为 375–400 章。同族联动标记可能减少实际章数，此处不提前扣减。
- 雅思每周 0–3 套，规划均值 **1.5 套/周**，即约 **78 套/年**。
- **每套平均按 1.5 次完整作答**，即约 **117 次完整答卷/年**。这与每周频率是两个独立参数，不能混为一次作答。
- 所有正式资产、不同答卷、原声、实际分析音频、多路原始返回、参考答案及有意义的历史版本保留。临时页及其独占资产仍按 48 小时销毁。
- 为偏上规划，全部雅思按完整模式计算；微缩模式降低题目侧容量，不将微缩的节省先计入预算。

结论：**免费保存全部内容有实际可行性，但“HF 100 GB + R2 小缓存”不能承诺覆盖全部密集场景和任意多年。** 应以至少 150–200 GB 的五年容量目标、200–300 GB 的十年目标选择可扩展永久层；付费缓存不保存唯一原件；可独立恢复的本地副本承担停付费后的保存保障。

以上目标不是今天要开通的容量，也不是限制教学内容的上限。未验证的免费账户、共享余额和学生优惠不算已经拥有的资源。

## 3. 日课完整词库

音频容量采用 `唯一朗读总秒数 × 码率 ÷ 8`。共享的第三部分句子只计一份；同一合成描述的重复点击复用既有文件。词族发音计入，不能只算 15,000 次单词朗读。

假设日课中的所有词汇、例句、文章句子最终至少点读一次，这比只估近期常用音频更适合永久保存目标。第一部分中英释义不是预先全量配音的当前要求；未来若新增整章朗读或整段释义音频，应另加实际资产，不能在本表中偷偷视为已覆盖。

| 敏感性情景 | 每主词例句数量 / 秒 | 每主词分摊的唯一文章句子 / 秒 | 原始点读音频 | 加入保留版本、正文及过程材料后 |
| --- | --- | --- | --- | --- |
| 较轻 | 6 / 8 | 1.5 / 9 | 7.74 GB | 9.79 GB |
| 中央 | 12 / 9 | 3 / 10 | 18.24 GB | 23.80 GB |
| 较密集 | 18 / 9 | 4 / 10 | 26.62 GB | 34.78 GB |
| 压力 | 24 / 10 | 5 / 11，码率按 80 kbps | 48.16 GB | 65.61 GB |

普通规划取 **15–35 GB**；压力规划进一步向上取 **80 GB**，为更长句子、更多义项与保留修订留空间。词条密度没有被协议限制，因此不能声称 80 GB 是全教材绝对上限。完成第一批合格正式章节后，应直接记录其例句数、唯一文章句数、时长与字节，替换这些假设；不需要批量生产完整词库来验证。

容量不靠降低 Bella 品质或删例句实现。相同文件的工作目录、请求传输副本不必作为独立学习资产重复占用永久层；不同的正式版本、用户原声和模型返回均保留。

## 4. 每套雅思与每年增长

将可以复用的试卷与每次作答产生的档案分开：

| 项目 | 假设 | 每套试卷 / 每次作答 |
| --- | --- | --- |
| 完整听力成品 | 30 分钟，128 kbps，含停顿 | 28.80 MB/套 |
| 保留的听力原台词片段 | 净语音 20–26 分钟，64 kbps | 9.60–12.48 MB/套 |
| 口语考官音频 | 3–5 分钟，64 kbps | 1.44–2.40 MB/套 |
| 题目、参考答案、定位与材料 | 文本及小型配套产物 | 1–3 MB/套 |
| 用户原始录音 | 净发言 7–10 分钟；压缩音频 64–192 kbps | 3.36–14.40 MB/次 |
| 实际分析 WAV | 同一发言，16 kHz、16 bit、单声道 | 13.44–19.20 MB/次 |
| 多路模型原始返回、描述、反馈、答卷 | 不重复存完整 base64 原声；包括文本回答与修订 | 2–8 MB/次 |

口语 Part 2 的准备时间和等待时间不应误当作净发言。若实际上传 WAV 而非压缩音频，或者保留较长的静音录制，这些都属于更大情景。

计算结果：

- 试卷侧：约 **40.84–46.68 MB/套**，重答复用。
- 单次作答档案：约 **18.80–41.60 MB/次**。
- 每套 1.5 次作答：约 **69.04–109.08 MB/套**。
- 再加 20% 的保留修订、有效补听等变动预算：约 **82.85–130.90 MB/套**。
- 78 套/年：计算约 **6.46–10.21 GB/年**，规划向上取 **7–11 GB/年**；压力规划取 **15 GB/年**。

没有采用固定“18 份口语”假设。按整套净发言总时长算原声，按实际各次调用保存证据。多模型调用使用同一份分析音频；`requestDescriptor()` 已将存档里的 base64 替换成音频位置和摘要，不额外乘四份完整 WAV。

保留变动预算表示实际留存的新文件；下一节的 20% 容量余量则是空闲空间，二者没有混称为同一份占用。Gzip 节省不预先扣除。

GitHub 的观点相应修正：无需把每条 MP3 提交进 Git 或不断新建仓库；如果采用 Releases，应保存与本项目发布相关的分章离线内容包和清单。它是有实际官方 API 的候选，不能因不熟悉管理方式排除，也不能将未公布数值上限解读为无限容量承诺。

微软候选的独立核查：现行文档说明 Azure DevOps Services 的 Git LFS 免费，Git 的 5 GB 单次 push 限制不计算 LFS 二进制；2015 年官方发布公告曾明确描述免费无限 LFS 存储，但旧公告不能单独充当 2026 年无限服务承诺。此处只确定“当前免费支持 + 值得验证大容量”，不把普通 Git 仓库的 250 GB 上限直接当作 LFS 配额，也不把它与 Azure Artifacts 的小额免费存储、Azure Blob 或学生试用混为一谈。[当前 LFS 文档](https://learn.microsoft.com/en-us/azure/devops/repos/git/manage-large-files?view=azure-devops)、[Git 限制](https://learn.microsoft.com/en-us/azure/devops/repos/git/limits?view=azure-devops)、[历史发布公告](https://devblogs.microsoft.com/devops/announcing-git-lfs-on-all-vso-git-repos/)

开户限制不能略去：当前“创建新组织”文档要求活跃 Azure 订阅，并在创建时选择订阅；现有组织和免费层不受此变化影响。定价页的 FAQ 同时仍写入门无需信用卡，两页存在入口信息差异，不能据此对本人的新账户承诺免绑卡即可开通。该候选可能仍需等待合格 Azure 订阅 / 学生通道。免费 Basic 前五用户和 LFS，与订阅开户资格是不同问题；私人项目的长期所有权也不应绑定以后会失效的学校账户。[组织创建要求](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/create-organization?view=azure-devops)、[官方价格及 FAQ](https://azure.microsoft.com/en-us/pricing/details/devops/azure-devops-services/)

Zenodo（CERN）也进行了核查：单记录 50 GB/100 文件，可申请一次性提高至 200 GB，但官方明确反对拆分同一大数据集来规避限额，以及单纯归档推广用途。当前项目是个人学习服务，未确认为合格科研数据集，因此不把多开 Zenodo 记录计入免费基座。[Zenodo 容量与公平使用](https://support.zenodo.org/help/en-gb/1-upload-deposit/80-what-are-the-size-limitations-of-zenodo)

## 7. 关系数据库同样需要冗余

Cloudflare 免费 D1 是每库 **500 MB**、每账户合计 **5 GB**、最多 **10 库**。现有两库加起来约 676 KiB 的只读快照，只能证明现在空，不证明未来所有资产索引都能塞进某一个库。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

按模型估算，普通点读资产可达到约 **20–40 万份**，压力接近 50 万份。假设资产记录、位置、引用和索引摊销为 2–4 KB/份，普通区间可约占 **0.4–1.6 GB**。这不是实测记录大小，但足以说明原设计不能只承诺一个 500 MB 资产库永久够用。

建议增量适配：

1. D1 保存业务状态、任务队列、章节入口、答卷索引和当前访问指针；大音频与原始证据作为文件。
2. 一章的完整资产清单作为可版本化文件保存，永久层保存其原件；D1 不必为每个不可变片段重复存整套描述。
3. 需要 SQL 查询的资产仍保留数据库索引，但目录支持章节 / 年度分区路由。单库达到约 300–350 MB 前启用新分区，而不是等 500 MB 写入报错后再补救。
4. 全部旧清单和证据永久可恢复；将查询加速数据迁出 D1 不等于删除历史。小文件可按章封装并保存成员索引，前提是验证范围读取和独立播放，不靠整包下载解决每次点读。
5. 账户 5 GB 与 10 库由其他项目共享，接入时先盘点。不能把新建库当成扩大账户免费总量。

这部分是针对真实容量风险的设计接口，尚未修改正式库或做大型重构。未来正文和答卷的年增长需实测；当前不能保证无限年 D1 足够。

## 8. 停止产出后的静态化与恢复

建议将保存和加速拆成以下通路：

```text
新正式资产
  → 本地可恢复档案（正文、音频、原声、证据、索引、必要恢复材料）
  → 免费永久层，核对摘要与可读取性
  → 近期在线缓存（可选）

历史访问
  → 当前缓存命中直接播放
  → 未命中读取已保存的原件，必要时补回缓存
  → 不重新调用 TTS、不因原件暂不可达而再扣生成费
```

具体取舍：

- **已有正常在线访问需求：** HF 先承担常用私有文件；R2 仅在确有性能需要且免费边界可控时使用，并允许禁用。
- **大而冷的原声、历次分析证据：** 优先进入大容量免费归档层；如果不能免费自动取回，应清楚标为需要本机恢复的档案，而不是伪称手机随时在线可读。
- **停止新增后：** 保留全部原件、索引与独立恢复材料；可以清除热副本、停止付费缓存，不丢唯一资产。保存独立读取的离线内容包，降低对服务器与 Codex 运行电脑的永久依赖。
- **免费平台的永久性：** “没有月费”不等于“任何年限不登录都不清理”。123 当前官方规则是连续一年未登录的免费账户冻结 30 天，再不激活可能清理；不能假设后台 API 调用一定符合其登录规则。[123 通知](https://www.123pan.com/Notice/150149)
- **付费唯一原件的风险：** Cloudflare 账单问题持续后有停服和删除条款；B2 同样有欠费停服、后续删除流程。将它们只用作可恢复副本，比提醒用户永远续费更符合目标。[Cloudflare 账单政策](https://developers.cloudflare.com/billing/understand/billing-policy/)、[B2 欠费规则](https://help.backblaze.com/hc/en-us/articles/219361957-B2-Non-payment-procedures)

本地第二份副本是空间占用，不是持续云租金；若以后需要专用磁盘，可以比较一次性购置成本。仅把不同文件分布到不同厂商并不能备份：一家丢失时，它独有的那一部分仍会丢失。备份容量不能同时当作主容量使用。

国内云盘及其流量包在用户最新偏好下不再推荐。Google Cloud 的原生 Cloud Storage 也没有提供本项目所需的大免费基座：Always Free 存储为 5 GB，免费跨境下行条件明确排除中国目的地；不能用一份小免费存储承诺整个手机访问链零费用。[Google Cloud Storage 定价](https://cloud.google.com/storage/pricing)

## 9. 研究后的选择顺序

1. **先确认 HF 能成为免费私有在线源**：一个小文件、一个长音频、私有授权、重复点读、iPhone Range 和实际账户余量。无需全量复制或批量生成声音。
2. **优先验证 Microsoft Azure Repos LFS 作为大容量永久文件源 / 备份**：以版本化学习项目资产为对象；确认免费资格、实际容量与服务条件，不将历史“无限”宣传当作免验证理由。与 HF 保持统一资产定位及摘要，不改变 PWA 的业务入口。
3. **GitHub Releases 作为另一份版本化内容包候选**，验证其私有下载和实际适配；不依赖不断分仓扩大承诺，也不把它变成 SQL 数据库。
4. Drive / B2 / OCI 用于有需要的补充分区；先查实际资源再决定，不预设全部开通。
5. 永久层的容量分配、目录路由与恢复导出应先闭合，再决定是否采用 R2 热层。付费永久存量仅在免费选项真正不足且用户接受后考虑。

本轮形成了容量模型和修订设计，没有宣称上述未开户或未实测资源已可用，也没有删减正式学习内容。用户返回后取消了完成通知，本轮没有发送该通知，不改变休息安排。
