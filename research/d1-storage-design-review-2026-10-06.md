# D1 方案独立复盘：修正过度文件目录化

日期：2026-10-06。研究结论修订，不更改线上协议、数据库或任何正式数据。

## 1. 复盘结论

用户提供的是参考思路，不是必须遵守的存储拓扑。项目真正目标为：正式资料永久保留；已有收费产物可靠复用；约 15,000–16,000 主词及正常多年雅思不逼近免费 D1 上限；可恢复、少运维、不新增持续账单。略慢可以接受，但不能据此接受额外的一致性缺陷。

**前版存在过度设计，不能仅回答“方案没有牺牲”。** 把所有永久小索引迁出 D1，会把 SQL 已提供的唯一性、查询及关系能力变成自建文件目录、并发合并、收据处理及检索适配；付出的不只是首访延迟。前版在追求 D1 绝对有界时，没有先充分测量紧凑永久索引能有多小。

修正推荐：**D1 保留可靠且紧凑的运行状态与核心业务/生成索引；OneDrive 保存完整正文、证据、历史和恢复包；只有实际需要释放容量时，按已验证的业务分区迁出旧索引。** 边界依然由容量预算和异常入口控制保障，但不提前重写全部关系查询。

## 2. 前版真正存在的代价

| 前版设计 | 实际风险/代价 | 本轮修正 |
|---|---|---|
| 所有声音身份只在永久文件目录查询 | 云盘故障时连“已有结果能否复用/是否可能重复收费”也依赖文件查询，归档空档需复杂核对 | 近期及规划容量内的完整紧凑生成身份索引留 SQL；异常领取与保护状态继续 SQL |
| 必建 4,096 个可变目录头及拆桶 | 组头并发发布、失效写入者、CAS 路径、收据合并和崩溃恢复需要自行实现 | 暂不作为基础设施；正常业务直接定位章/套/答卷，文件摘要已有确定路径 |
| 固定槽位重用所有业务记录 | 自然 ID、外键和历史关系需要大范围适配；槽位重新使用引入额外身份风险 | 保留普通稳定业务 ID；缓存有限数量，工作队列做字节/数量入口控制，不强制环形槽位 |
| 从开始就把所有旧题检索改为年度文件搜索 | 现有 SQL 查询与题型/USE 关联全部重写，跨年搜索变慢、功能漏失风险增大 | 留有价值的结构化查询和短检索字段；大材料先外置，旧分区按压力逐步迁出 |
| 每次新增资料另建收据、并更新多种清单 | 事务边界更多，文件数和请求增多，归档延迟可能影响新资料发现 | 只为可靠提交、收费意图和独立恢复需要的记录留提交证据；普通数据归入业务版本包，不一律另造多层元数据 |
| 到 200 MB 一律停新任务 | 属于最终故障保护，不能替代提前迁出和空间规划 | 在较低阈值维护；阻断只发生于维护失败或异常增长，不作为正常日用节奏 |

保留紧凑 SQL 索引不是要求永远所有历史都留 D1。它是优先使用现成数据库能力，后续超出预算时再启动已有永久分区的读取适配。

## 3. 新的对照容量证据

新增 research/d1-compact-registry-model-2026-10-06.mjs/.json，完全本地执行，无 API、收费模型或生产写入。

模拟一张成功音频结果表：INTEGER PRIMARY KEY（保留当前备份游标的 rowid 兼容）、32 字节完整生成摘要及唯一索引、32 字节文件摘要、字节数与 MIME 编码。调用状态单独存小表，成功行不存完整文本、冗长 JSON、逻辑路径或历史版本。

| 成功结果数量 | SQLite 分配空间，含唯一索引 | 平均分配字节/条 |
|---:|---:|---:|
| 500,000 | 62.47 MB | 124.94 |
| 700,000 | 87.62 MB | 125.17 |
| 1,000,000 | 125.03 MB | 125.03 |

三种样本 integrity_check=ok；EXPLAIN 验证按完整生成摘要使用唯一索引查询。没有截短摘要、压缩、删除历史结果或忽略 SQL 索引成本。

**这不是整库容量，也不是生产 D1 性能验证。** 它没有计算章节关联、题干检索、历史关系、异常队列、物理碎片及其他表；这些需单独分配预算。它证实“几十万成功声音身份必须全部移出 SQL 才能避免 500 MB”并不成立。

前版 36.52 MB 模型只证实人为设定的槽位结构很小，没有比较其对现有功能的适配成本；不能据此证明它是本项目最合适的工程方案。本轮证据纠正这一选择偏差。

没有直接采用 WITHOUT ROWID。该优化对某些键可能省空间，但当前 storage-scan.mjs 依赖 rowid；直接替换会破坏已修复的归档通路。应按兼容性和收益决定，不为省少量空间扩大本轮范围。[SQLite 官方说明](https://www.sqlite.org/withoutrowid.html)

## 4. 修正后的实际组织

### 主 D1

继续保存身份、设置、章节及版本入口、当前阅读状态、答疑工作状态、额度汇总等。可把成功音频的紧凑身份与结果目录放主库，承接目前 storage 三表的较大重复开销；最终落库要根据真实两库余量和跨库调用成本决定，不在本轮先迁表。

对于生成身份保留完整摘要和结果定位。不必在同一库为每段音频同时保存全文请求、长逻辑路径、重复 MIME、当前版本行、历史版本行、位置行和所有章节关联。哪些字段可以计算、哪些必须持久保存由实际读取决定。

已有内容按 SHA-256 放在 OneDrive 的 objects-xx/<完整摘要>.bin；知道完整内容摘要及应用目录，就可以通过确定路径获取，避免再维持另一份永久 itemId 总索引。近期 itemId 可缓存；路径稳定性和用户移动目录后的恢复需核验，不能宣称确定路径比所有 ID 模式永远可靠。[Graph 路径与 ID 寻址](https://learn.microsoft.com/en-us/graph/onedrive-addressing-driveitems)

### 练习 D1

保留套卷、题目、作答等稳定 ID、必要关联、题型/USE 查询字段、当前状态及参考答案揭示状态。需要频繁查询或确实有功能价值的短题干/搜索字段可保留，不为了“D1 必须只存当前数据”把每个 SQL 条件改成文件查询。

试卷长材料、参考答案全文、答卷全文、批改全文、模型错误全文、录音和原始证据外置，SQL 留有验证的引用。源范围仍是第一章至当前全部已发布内容、本章显著加权，不能因为存储优化改变教学选材协议。

历史数据量如果很低，可继续保留小型 SQL 关系，不必定期机械搬迁。某一类达到自己的字节预算时才归档其旧分区；需要跨期检索的索引页在归档时生成并验证，保持全历史可查，不静默限定近期。

### OneDrive

保存完整的按章/按套/按次档案和所有有意义的版本；已有音频和原始字节不因数据库瘦身重新合成或丢失。业务清单负责关系与原件恢复，小 SQL 索引可以由档案重建。

在规划范围内，正常点读查询不必先取全球文件目录；普通页面读取一个业务资料包即可。稍慢用于大内容首次取回，不能成为降低状态一致性或增加大量请求的理由。

## 5. 仍然需要的容量边界

两个库各自单独预算：初期各以 100–160 MB 为规划区间，而不是为了追求同一数值强行迁走某类小索引；具体分项以实施后的物理 file_size 验收。维持 200 MB 的新增积压保护线，离免费每库 500 MB 留约 300 MB 故障余量。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

这不是新的生产配额配置。120 MB 起检查增长最大的类别；160 MB 前必须完成验证后的容量释放或停止扩大可替换缓存。200 MB 是维护失败情况下的应急保护，正常使用不应该靠用户频繁碰到暂停来保证容量。

成功音频索引也有预算。规划约 50 万份全词库，加多年听力/题目音频及修订仍需冗余，70 万及 100 万条是敏感性样本，不是资产数量硬上限。假如紧凑索引本身接近预算，就按生成期/业务归属封存旧结果分区，D1 留分区定位和近期结果；未命中必须先查旧分区，不能当作未生成。

长期异常、未知计费、未提交答卷不能直接淘汰；积压达到明确的小字节/数量上限时拒绝新增长并告知。合法长输入进入永久文件，不因行大小上限截断。文件故障时允许少量有界应急副本，不允许无限 D1 音频 BLOB 回退。

为了处理有限存储与无限生产的矛盾，仍必须有最终入口保护。正常永久资料不删除，已验证可恢复的 SQL 副本才能轮换。物理删除可能只释放可复用页，仍以真实 file_size 判断，不承诺立即缩小文件。

## 6. 新发现的备份约束不能漏掉

把紧凑永久索引留 SQL，会增加 SQL 行数。不能因此在每次任务末尾完整扫描 70 万行，更不能认为二进制编码会减小 D1 rows_read：额度按实际扫描行数计。[D1 计量](https://developers.cloudflare.com/d1/platform/pricing/)

成功结果应设计为追加且不可变，重生成采用新的有效生成版本，不静默修改已成功结果。大追加表首次建立核验检查点，以后仅导出已提交游标之后的新行；不可变检查点块与增量块进入独立恢复清单。其他有界的当前状态表继续完整快照，避免为了几千行构建通用变更捕获系统。

如进行旧分区迁出、修复或 schema 变化，要显式建立新的检查点及在线截点，不把存在删除/修改的表冒充 append-only。恢复应能重建在线索引并保持历史永久分区；增量状态只有在回读和恢复关系验证通过后推进。检查点版本及失败恢复必须实际验证。

这属于实施前置项，不是已上线功能。现有游标修复和读取保护继续运行，不在本轮改成未经验证的增量备份。

## 7. 安全提交需要保留，但不过度包装

采用各业务现有稳定 ID 和 D1 原子领取/完成，完整内容先上传回读再提交小引用。D1 与 Graph 没有跨系统事务，需要允许未引用文件，并通过幂等 ID 回收/续提交；不能靠把步骤画成箭头就宣称原子成功。

收费意图、结果未知和目录未完成状态仍有明确持久证据。正常重试复用身份，云盘错误不视为不存在；只有确定未曾收费且具有效领取才可发起调用。永久业务包与恢复清单承接独立恢复，避免每一类数据另造两份收据和三层目录。

如果要更新已有 OneDrive 文件，小文件 PUT 的冲突控制不能仅由某个上传会话例子推断。优先上传不可变版本、D1 原子切换少量当前指针；独立恢复头由已有单写者发布并保留可发现的不可变恢复清单。必要条件写入路径仍需试点验证，不能用未验证 CAS 作为全部元数据正确性的前提。[Graph 上传会话](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)

## 8. 实施建议与保留代价

1. 先把大内容和重复描述外置，测量真实紧凑目录及其他表占用，保留现有 SQL 路由所需的小关系。
2. 成功音频归一化，原声证据和章节/试卷版本仍完整保留；核对旧链接、全历史复用、未知结果保护和 Microsoft-only 恢复。
3. 最大追加索引实现独立检查点/增量恢复，再正式开放其规模增长；其余小表继续已有快照。
4. 基于真实容量迁旧分区，不预建固定 4,096 个可变目录头，不强制重写所有题目检索和外键。
5. 最后落实缓存和异常边界、物理空间及账户读写统计；旧 SQL 行迁出必须通过真实功能与恢复验收。

代价仍包括：大文件首次读取更慢、云盘授权和订阅依赖、跨文件不再有 SQL 外键、需要维护引用与检查点；修正后把这些代价限制在真正适合文件存储的内容上。生产迁移及性能验证尚未发生。

保留轻量 SQL 索引并不是背离永久保存目标，反而保留了数据库已有能力。全文件目录化仍可作为未来极端增长的备选，但不是当前项目必须付出的工程复杂度。

最终判断：前版的分层方向合理，迁出范围过大；应采用紧凑关系索引与永久文件档案的混合方案。容量安全来自真实字节预算、提前迁出与故障保护，不来自迎合某一种用户描述的分层形状，也不来自把 D1 压得越小越好。
