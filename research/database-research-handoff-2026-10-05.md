# 第二语言：项目全景与数据库、文件存储研究交接报告

整理日期：2026-10-05，北京时间。

读者：此前完全不了解本项目、开发中的 Codex、用户历史讨论及已用资源的外部 Chat 模型。

用途：提供足够背景，支持独立研究本项目的数据库与长期文件存储方案。本文不是迁移执行指令，不要求接受既有排序，也不构成已启用的新协议。

## 0. 先读这一页

**第二语言是一个已部署的、单人使用的英语学习 PWA。它由 Windows 上的 Codex 生产课程和反馈，Cloudflare 承担网页、认证、API、任务状态和模型出口。**

目前需要解决的首先是媒体与原始材料的长期存储，以及免费 KV 每日写入次数容易耗尽的问题。不是已有关系数据库装满了。

截至 2026-10-05 已有只读查询快照：两个正式 D1 数据库合计约 676 KiB；正式练习音频表尚无记录，没有一套正式全流程雅思练习的长期存储实测。2026-10-04 的事故是测试设施耗尽整个账户的 KV 每日 1,000 次写入，部分新增文件通路受阻，原有读操作、D1 登录与其他不使用 KV 的项目并没有因此全部瘫痪。

用户正在研究是否长期保存全部有价值产物，包括音频、自己的原声、多路模型原始返回、历史版本和中间文档。这个选择尚未最终实施。免费大容量自管 OCI、GitHub 分仓文件库、现有 D1 配对象存储，均应作为候选研究，不能仅因“难管理”就排除前两者。

请始终区分四种能力：

1. **关系数据库**：状态、索引、关联、领取任务、答卷版本、事务。
2. **文件或对象存储**：音频、原始 JSON、Markdown、导出与备份。
3. **运行服务器**：操作系统、文件服务、数据库进程及其维护。
4. **缓存和静态分发**：提高复播速度，减少上游读取；不应独自承担唯一历史副本。

200GB 虚拟机磁盘不能直接与 25GB 托管数据库或 10GB 对象桶按容量排名。需要比较能否组成适合本项目的完整通路。

## 2. 教学产品及其数据语义

### 2.1 每日日课：40 个主词、完整三部分

北京时间每天 03:00，由本机计划任务启动 Codex CLI，载体为 `gpt-6-sol`、推理强度 `high`。电脑、项目文件、登录和必要网络权限必须可用。

选词来自 VIX 通用英语辅助索引中尚未标注的词。索引经过优先级词表占有去重，一个词不能因属于多个原词表而重复作为多个候选。推荐是加权概率候选与模型对用户学习价值的判断结合，不是必须从历史章节重新“选材”。

- A1/A2 显著降低推荐概率。
- B1/B2/C1/NAWL 对雅思学习给予小幅偏好。
- C2/COCA/TEM4/TEM8 仅相对降低概率，不彻底禁选。
- 同族派生与变体需要模型识别和一并处理，最终以主词推荐。
- 正式推荐完成后标注 VIX 辅助索引；目前标签是实际北京时间的 `YY-MM-DD`。章节日期为 `YYYY-MM-DD`。

三部分结构：

1. **词条与用法**：按字典序排列主词；全量提取 Collins、Oxford 两份 textbook 的有关内容，包含相关派生。以 Collins 义项为主对齐，Oxford 独有义项按相应风格补建。一级标题为词；二级为各义项、相关派生等。音标和标题按照现有产品排版。例句在这一部分提取，不打印在正文用法说明里；缺少例句的用法可补建。
2. **例句**：按词排列所提取和补足的全部例句，配等宽样式译文，与第一部分用法对齐。
3. **原创文章**：自然使用第一部分全部目标用法及其下级用法，不漏项；逐句配连续语义译文。创作主题与剧情尽可能自由，不加与质量目标无关的额外限制。

正文是任务目标产物，不应显示工程审阅过程、来源管理解释或运行日志。来源材料和建设记录可以保存，但不污染课程阅读正文。

### 2.2 编码、阅读状态与复用

章节内词条、用法和例句有唯一编码；第三部分句子有 `SENTENCE` 身份，真正运用目标用法的句子关联 `USE`。跨章节使用 `章节ID#USE编码` 等复合身份，不能把两个章节的同名编码混在一起。

读者可以开启用法高光并跳到第一部分，再跳到对应例句；第三部分可开启逐句译文。各部分位置持久保存。听读资源需要绑定章节或题目版本及摘要，后来修改文字不能让旧音频静默冒充新音频。

前端维持完整的 2008 风格、iPhone 视口与锁定缩放。数据库研究无需重做 UI；后端升级应该保护现有登录、阅读位置、章节索引、音频按钮和已存答案。

### 2.3 内容生产的中间文件

Codex 可自由建立中间文档，降低把全部工作记在对话上下文中的负担。逐词材料去向、例句映射、分批处理结果、文章权威草稿、连续性记录、覆盖核对和下一步都在 `work/` 中。

现行协议先解决长篇质量下降，允许第一、二部分分批、第三部分总规划与分批续写。迁移存储不能把详细材料替换成摘要，也不能要求模型每次重新生成已有内容。

### 2.4 休息、临时页和复习

- 默认关闭的休息开关：下一次日课运行读取后跳过该次推送并复位。由用户设置；数据库研究不能擅自改变安排。
- 临时需求是一次性开关和输入框，发布对应需求后复位，注意保留后来新改写的需求。
- 临时测试可推已有测试文档；测试不占正式日历、不改正式日课运行、不标记 VIX。
- 复习只从已经发布的正式章节原样提取第一、二部分与第三部分对应原句及译文，按词排版，不重新创作第三部分。
- **当前临时页发布后 48 小时失效，并清理正文、索引及待发通知；不离线缓存临时正文。**

用户现在考虑全量历史保存，可能将临时页改为“阅读入口 48 小时失效，私有档案仍保留”。这只是候选，需要显式修改生命周期协议；不能说当前已如此运行。

## 3. 雅思第四部分：申请、题量与作答链路

### 3.1 只有两种申请

现行申请是完整雅思或微缩雅思，两者均有听力、阅读、写作、口语。不再由用户点选四科，不提供听读混合规格。展示顺序为听力 → 阅读 → 写作 → 口语；不要求一次坐完四科。

| 科目 | 完整雅思 | 微缩雅思 |
|---|---|---|
| 听力 | 四段，每段十个计分空位，共40题；约30分钟 | 保留四种情境，每段六题，共24题；目标约18分钟 |
| 学术阅读 | 三篇40题，2150–2750词，60分钟 | 三篇各八题共24题，1400–1900词，35分钟 |
| 写作 | 完整 Task 1/2，建议20/40分钟 | 同完整规格 |
| 口语 | 完整 Part 1/2/3，约11–14分钟 | 同完整规格 |

微缩是个人项目规格，不是 IELTS 官方考试。用户要求微缩覆盖全部已支持题型形式，排除通常难度分布的下段。完整卷按自然 IELTS 规格组合题型；官方并不要求一卷包含全部题型。题目难度标签及模型审阅不是经考生统计校准的测量难度，不换算未经校准的官方 band。

### 3.2 来源范围：所有历史都可用，但不等于全部正文每次塞入上下文

申请固定第一章至申请时最新发布章的 ID、日期和正文 digest，以及焦点章，默认最新章。焦点章给予显著判断注意力；如果不适合考题，可以自然使用旧章。

题目接近真实雅思，不要求使用本章指定单词、不机械覆盖40词、不把第三部分文章改成考试题即可交差。每题有自然关联的来源章节；正文选入后回读原文，摘要索引只用于导航。

随着章节增长，可以维护增量主题和表达索引。**必须区分保留完整历史清单，与每次把全部历史正文放入模型上下文。**前者是当前来源可追溯要求；后者不是当前协议要求。研究不应擅自把来源范围缩成最近几章。

当前 `source_json` 有完整历史元数据快照，同时存在关系来源表；将来可能重复增长。外部模型可以分析是否用共享不可变来源版本或对象清单减小重复存储，但需要保留旧练习当时的来源版本，不静默改写。

### 3.3 题目、参考答案与答卷

口语 Part 1/3 默认听考官音频，题目原文可主动揭示并记录；Part 2 题卡可见。写作题目为可见文本/数据。口语写作参考答案为约7.5水平的隐藏文本教学示范，不是唯一答案，也不是官方认证分数。

隐藏不是浏览器 CSS 藏起来：未主动揭示前，后端不发送参考文本。

各次作答形成不可变 attempt，绑定题目与答案版本；重答建立新 attempt。批改队列有领取身份、租期和幂等完成。反馈保留优势、重要改进和重答建议，不要求照抄参考答案，不因没用课程词汇扣分。

原始选择答案、作答时长、实际播放条件、提前揭示等条件都应保留，不能用后来的修订覆盖旧尝试。雅思练习长期保存，独立于日课与临时页，不写 VIX。

## 4. 音频工具池、费用与保真要求

### 4.1 朗读与音源复用

当前合成模型为 OpenRouter 的 `hexgrad/kokoro-82m`。

- 所有非听力朗读固定 Bella (`af_bella`)：点击词汇、句子、文章及口语考官。
- 听力九女声：Alloy、Aoede、Bella、Heart、Jessica、Kore、Nova、Sarah、Sky。
- 听力五男声：Eric、Michael、Liam、Puck、Fenrir。
- 按整份脚本的人物台词量均衡随机路由，同一人物固定音色，同场人物可区分；不为均衡而改变雅思男女角色结构。
- 用户已否决男声调音实验，不采用处理版本。
- 点读按需生成与缓存；**没有每天给整章全量配音的强制任务**。
- 相同文本、模型、声音和参数的摘要命中后复用已有音频。复播没有新的 TTS 模型费，但可能有数据库、存储读操作和流量费用。

此前2026-10-05研究核对 Kokoro DeepInfra 路线为 $0.62/百万字符，Together 路线为 $4/百万字符；当前代码未固定供应商，不能保证每次最低费率。此处是已有价格研究记录，不是本次重新调用模型的实测。

### 4.2 口语回答分析不是 TTS

默认每份原声由四路全量采集，然后 Codex 综合接管：

| 路线 | 当前配置 | 用途与局限 |
|---|---|---|
| Whisper | Cloudflare Workers AI `@cf/openai/whisper-large-v3-turbo` | 转写与提供方实际返回的时间信息；不凭文本证明发音、节奏 |
| Gemini | OpenRouter `google/gemini-3.8-flash` | 原声观察、完整结构化报告；细粒度语音判断仍需审阅 |
| Qwen | OpenRouter `qwen/qwen3.8-omni-flash` | 全量报告及按具体目标多次补听；同模型多次不是独立共识 |
| GPT Audio | OpenRouter `openai/gpt-audio` | 额外原声细节；输出文字分析，不是生成音频 |
| 腾讯智聆新版 | 已购口语评测包、本机定向适配 | 可选词/句音素等资料，使用确认的本人原话；不强制所有回答全量评测 |

Azure、直连 Google、直连阿里等有冗余位置，未作为已开通主通路。

OpenRouter 所有模型和 Kokoro 共用同一个钱包，模型多不等于资金通道多。Whisper 免费用量在 Cloudflare，腾讯套餐次数是第三个独立额度池。

OpenRouter 请求必须走已验证的 Cloudflare 后端出口。本机直接调用曾遇地区或资格问题，不能把存储迁移顺便改成未经验证的模型出口。新存储后端可以只管文件，不必负责推理。

每路要求尽量明确 prompt、适配的 JSON Schema/最终 JSON。保存完整请求、原始返回、解析结果、状态和账单；不能把三个报告摘要成一个段落后丢弃原证据。HTTP 200、已收费、finish=stop 都不证明获得有效报告。Qwen 曾出现空数组、报告套单元素数组及思考计费波动，原始返回必须保留。

Codex CLI 的教学接管不能被假定为直接像人一样听取任意原声；当前通过音频模型的原声取证、可回查原文件和工具材料进行判断。没有音频证据的转写只评价文本维度，不虚构声音测量或 IELTS 评分。

### 4.3 任务结束后的余额快照

所有实际日课、发布、复习、测试、练习、批改、声音分析等工作末尾查询额度，保存核对时间和核实/估算状态，更新 PWA 余额页。浏览余额页只读上一次记录，不每次重新查询。

预算单位为用户一次完整学习流程，例如日课加完整雅思，包含首次声音、核对、一次作答和反馈；不是一次脚本或一次 API 调用。每个服务按自己的计量单位管理，仅当不足三次最大任务的预计上端时告警。Codex 订阅不在这个可查余额系统内。

当前腾讯包为9.9元/10,000计费次，用户2026-10-05截图已用22、剩9978、有效至2027-10-02，具体到期时刻未展示。公开查询尝试未取得实时套餐余量；目前用截图基准与真实调用账本计算，不把现金余额当套餐次数。

Whisper 按每天10,000免费 Neurons 及实际使用估计，UTC零点/北京时间08:00刷新，不设计 Whisper 充值。

OpenRouter 不足时停止新增收费调用，保留已有材料。没有自动跨日重试；只有用户充值后明确要求继续才处理。未知是否收费的请求不得盲目重跑。

### 4.4 已有条件成本研究，不能当正式整套账单

此前使用本人一份录音的不同长度，经独立 Cloudflare 测试设施取得九次账单，合计 $0.116360984。由此及已有材料进行估算：完整雅思首次完整流程正常情景约 $0.44–0.80；余额页保留约 $0.35–1.34 的更宽规划余量，日课加完整雅思约 $0.35–1.38。

14/18/22份原声、净回答7/8.5/10分钟是敏感性情景，不是雅思固定问句数或本项目强制题量。官方口语整场11–14分钟包含考官与准备，不能全部按学习者录音时间计费。

存储比较不要把模型预算算进数据库价格，也不要以便宜 TTS 推断整个口语分析都便宜。更换存储不会自动降低已采用的多路分析费用。

```text

   ├─ 主D1：认证、日课、阅读、控制、通知、余额
   ├─ 练习D1：题目、来源、答卷、状态、原声任务/调用索引
   ├─ CHAPTERS KV：不可变正文
   ├─ PRACTICE_MEDIA KV：听力/考官音频、原声与分析资产
   ├─ Workers AI：Whisper
   └─ OpenRouter：Kokoro、Gemini、Qwen、GPT Audio

Windows计划任务 → Codex CLI → 授权发布/领取接口
   ├─ work目录：详细建设文件、草稿和续作记录
   ├─ ffmpeg：转码、拼接、实测音频时长
   └─ 已有腾讯云定向评测适配
```

- D1 是 SQLite 路线，现有代码大量使用 `prepare(...).bind(...).first()/all()/run()` 与批处理；换数据库不是只改域名。
- 前端单人 Passkey owner 与会话认证；Codex 采用单独发布身份。没有开放匿名个人原声访问。
- Worker 配置每分钟 cron，用于既有通知、过期清理与声音任务采集等云端工作。它不是每分钟启动一次 Codex。
- 日课本机03:00；练习本机轮询此前配置为30分钟，入口先检查队列，空队列退出，不运行 Codex。不能把“正在聊”当成可靠的全天候后台处理器。
- Windows 原声准备使用 ffmpeg 转换，不裁剪或修复本人话语；Cloudflare 采集，再由本机 Codex 领取保真材料完成反馈。
- 未来文字疑问功能已讨论：对章内某句提交问题，D1 排队，电脑在线时由 Codex 处理与回推；**尚未建设上线**。一分钟一次空队列查询约1,440次/天，不调用模型，但会产生 HTTP/数据库读取。

### 7.2 2026-10-04 KV事故

测试构建220个音频，原设计每片段写启动、请求、音频、返回和处理版等约五份，再加余额与清单，计划约1,138次KV写入。账户当天其他用量叠加，耗尽免费1,000次 put。

Cloudflare邮件与 `KV put() limit exceeded for the day` 确认了原因。免费写入UTC零点重置；北京次日03:00早于08:00重置，不能以“跨了本地日期”判断已恢复。

事故后试听文件转为既有静态资源，反馈改独立D1及本机导出，没有重新付费生成。**新增namespace只隔离数据，不增加账户免费次数。**

当日账户统计为D1读38,212行、写2,586行；远低于D1免费日额度。KV分析统计显示写1,248，但不应把分析仪表的聚合数冒充精确账单或超限成功次数。

已有页面、读取和D1身份未因该put额度全部停摆。课表与VIX现行部署不使用该KV绑定，本事故不能推广成全部正式项目瘫痪。

### 7.3 现行免费资源相关限制

| Cloudflare产品 | 与本项目有关的免费额度/限制 |

| Workers | 通常免费每天100,000请求；各入口和绑定调用的实际计量不能简单拿日志条数相加代替账单；CPU等另有限制 |
| Workers AI | 每天10,000免费Neurons，与KV/D1不是同一额度 |

独立数据库或namespace不是独立账户额度。Word数、API次数、D1行读写、Neurons、存量GB与GB-month不能混为一个“剩余百分比”。

### 7.4 正式口语也可能产生较多KV写入

按现有文件路径粗数，每份原声可能包括：原始音频/快照、WAV/contract、四路各自request/raw/metadata/parsed、总manifest和反馈，正常路径约22次写入。14–22份回答可能约308–484次，之后还要计算听力合成片段、核对、重试和其他任务。

这是代码路径估算，不是正式一套考试的实际计量。它说明即使不做巨大试听，媒体直接落KV的每日写次数仍需认真评估。只是加大数据库容量不能自动解决这个限制。

## 8. “全部存下来”应该研究哪些材料

用户尚在比较全保留与有限缓存，不应替他提前定删除周期。

全保留候选至少包括：

1. 正式章节每次版本、结构化编码、逐句译文、来源教材提取与映射。
2. 词汇推荐选择、有关VIX索引版本与标签、章节与词族关系。
3. 雅思申请、题目、隐藏示范、答案证据、来源快照及修订。
4. 用户历次选择答案、写作、口语原声、重答和完整反馈。
5. 转换后实际提交各模型的分析音源。
6. 模型每次请求、完整原始返回、解析结果、失败与账单资料。
7. 点读音频、听力角色片段、成品音频、考官音频与时间定位。
8. Codex确实写出的中间文档、权威草稿、续作说明和版本化协议。
9. 有用途的测试文件、评分与研究输出。
10. 数据库导出、文件清单和必要恢复配置。

这里的工作记录指实际文档、工具结果和版本，不是不存在的模型内部思维日志。不要为了“全量”要求额外披露内部推理。

全保留也可以做字节摘要去重，多个逻辑记录引用同一物理文件；必须保留各次调用身份与上下文，不能因文本相同而合并掉两次不同模型调用的历史事实。

ffmpeg可重新产生的拼接临时PCM并不等于必须永久保存的教学证据。若用户最终要连这些都存，需单独列成本，不暗中删原声或原返回。

## 9. 容量估算：条件、公式与未知项

### 9.1 已核对的编码与估算

- `scripts/practice-audio.mjs` 最终听力MP3编码为128kbit/s。
- `scripts/speaking-practice.mjs` 分析WAV为16kHz、16bit、单声道。
- Kokoro一个本机4.73秒样本约57kbit/s，这是样本观察，不是所有供应商保证码率。

按十进制MB计算：

| 数据 | 公式/条件估算 |
|---|---|
| 30分钟128kbit/s MP3 | 约28.8MB |
| 18分钟同码率MP3 | 约17.28MB |
| 分析WAV | 每分钟约1.92MB，7–10分钟约13.44–19.2MB |
| 100小时128kbit/s成品音频 | 约5.76GB |
| 1,000小时同码率 | 约57.6GB |

口语原录音格式、各合成片段、请求是否内嵌base64音频、JSON报告长度、重答与重试会改变存量。**尤其完整请求如果包含base64，可能与独立音频形成重复保存，编码体积约增加三分之一。**是否可保存一个可无损还原请求的引用式包装，需要结合现行“完整请求保真”要求单独研究，不能声称当前已优化。

### 9.2 长期规模情景

已有早期规划用每套完整雅思60–120MB作为基础区间，包含主要音频与材料；没有正式整套实测，也未证明充分覆盖所有嵌入音源请求、补听、历史版本和备份。

- 每月4套，基础线性推算每年约2.88–5.76GB。
- 每月8套，约5.76–11.52GB。
- 点读、重答、额外题集、修改、测试、全量中间材料与副本另外计算。

请外部模型把60–120MB视为需要完善的初步基线，而不是全保留方案的容量上限。应分别估算文字/关系数据、长期音频、每次模型报告、重复嵌入请求与备份倍率。

日课每次40主词不代表每天必定生成40个固定音频，更不代表全章全量配音。点读增长应按实际点击和摘要复用率建情景。

## 11. OCI 200GB：能够维护，但不是托管承诺

### 11.1 资源与容量

最新官方资料为A1总2 OCPU/12GB RAM；免费块存储200GB包括系统盘与数据盘，最多五份卷备份。不要采用旧教程的4核24GB额度。

可讨论约50GB系统盘+150GB数据盘的配置；数据空间需留日志、临时转换、数据库维护余量。规格足以支持本项目个人文件服务和关系数据，但没有本项目实际服务器压力测试。

### 11.2 Codex可以做哪些工作

取得SSH/OCI权限和可用执行环境后，开发中的Codex可以：

- 建设私有文件API、部署服务、接入现有后端与索引。
- 配置系统服务启动、异常重启、定时磁盘/健康检查。
- 配置日志轮转、增量备份、摘要核对、恢复脚本。
- 处理系统安全更新、服务修复、凭据更换与必要恢复。
- 若迁数据库，负责一致性备份、SQL迁移、索引及恢复。

自动任务是普通服务器程序，不需要全天持续调用Codex；复杂修复仍需要唤起Codex且执行环境、网络与授权可用。不能把本对话当作已存在的全天候托管运维。

### 11.3 实际风险

- 注册需要合格信用卡或可按信用卡使用、不需PIN的借记卡；银联储蓄卡是否可注册并未验证。学生身份不自动解决绑卡。
- 免费机型可能out of host capacity，恢复时也不保证立即有空闲容量。
- Oracle声明免费闲置实例可被回收：连续七天CPU第95百分位、网络以及A1内存利用率满足其低于20%的条件。本单人项目负载低，存在真实可能。
- 运维脚本不能保证平台不回收；没有“做个健康检查就绝不回收”的官方承诺。
- 免费卷备份最多五份是滚动恢复资源，不是跨平台永久副本；重大资料仍应有独立备份。
- 不会为了免费容量自动升级付费账户或购买资源。升级后资源计费与回收政策应另查，不能凭社区说法保证永远不回收。

初步接入建议是OCI只负责文件，Cloudflare/D1继续管理用户入口与状态，避免为容量把所有已运行部分同时搬走。若研究发现完整迁移明显更优，可以提出具体证据和渐进路径。

## 12. GitHub分仓：用户提案已经证明技术方向成立

### 12.1 逻辑存储与增量

用户提出：把每章或一批章节的文件放入不同仓库，后端索引对应仓库；逐步增加仓库形成大库，已有音频迁移后直接复用。

这在技术上成立。D1可以记录 `owner/repo/commitSHA/path/digest/bytes/mime`，Cloudflare按定位读取；不需要克隆全部仓库，更不需要重新合成音频。多仓由程序维护，不应仅用“难记忆或难管理”否定。

它能成为分片文件库。实时状态、领取任务和事务仍可留在关系数据库。按容量滚动分仓不必每章都新建一个仓库；只是设计候选，不是已确定必须按月/年或固定阈值。

### 12.2 当前已核对的限制

| 项目 | 官方信息 |
|---|---|
| 仓库数 | 每账号/组织最多100,000；50,000后提示 |
| 普通Git账号总GB | 本轮未找到公开固定总配额或无限容量保证 |
| 单仓建议 | 新版limits建议`.git`≤10GB；另一大文件页仍建议更小；都不是赠送10GB的容量承诺 |
| 单文件 | 普通Git阻止超过100MiB；Git推荐二进制用LFS或对象存储 |
| 单次push | 2GB硬限额 |
| 普通令牌REST | 每用户通常5,000次/小时，共享账号限额，不随仓库数增加 |
| 写入频率 | 有二级限流，通常创建内容≤80次/分钟、≤500次/小时；端点还可能更低 |
| LFS | Free/Pro账户10GiB存储与每月10GiB下载；分仓不会增加 |

GitHub可对过量带宽和基础设施负担限制、暂停或要求调整。既不能把低频私人学习文件武断判为违规，也不能承诺100,000×10GB的保证免费空间。

### 12.3 私有读取与版本

私有材料不能为方便访问而公开。访问凭据在Cloudflare后端；PWA沿用登录。GitHub Contents API支持固定commit读取、较大文件raw媒体类型；download_url可能过期，索引不能只存一个临时下载URL。

新增先写文件核对摘要，再登记索引；修改建立新文件版本并切换当前指针。删除当前路径不会删除Git历史；彻底清除需历史清理。用户希望保存全部历史时，版本保留可以是优势。

需要独立样本核实：Cloudflare到私有仓库的延迟、iPhone播放、Range拖动、单文件读取开销、令牌授权新仓范围、批量增量写入和备份恢复。不能假定原始GitHub链接在中国iPhone网络一定稳定。

Release附件也可作为不同文件通路研究。官方描述软件发布附件与普通Git不同的大小/总量规则，但不能把该描述当通用无限空间与可用性保证；LFS、Release和普通Git要分别评估。

## 13. 渐进迁移建议与真实工程边界

这部分是可以讨论的工程框架，尚未实施：

1. 保留D1中的权威任务、会话、答卷和目录，文件位置增加明确存储类型。
2. 统一资产定位包含：`assetId / backend / key或repo定位 / digest / bytes / mime / logicalOwner / revision / lifecycle`。
3. 同一摘要可以复用物理文件，但各章节、attempt、模型call保持各自关联。
4. 外部文件成功写入并校验后，才使数据库指针可见；不存在D1与其他云之间天然原子事务。
5. 迁移先复制、校验、切读取指针；保留旧位置直至确认恢复可用，不提前删除原件。
6. 老文件按原backend读取，新文件写新backend；避免“绑定新桶就把老KV读丢”。
7. 音频受控读取、支持Range与尽量流式返回；不要每次拖动都全量加载长音频进Worker内存。
8. 文件生命周期按明确的用户选择执行。共享资产需要判断引用；临时页过期不应误删正式音源。
9. 保留原有模型出口、声音身份、余额更新和无重复付费保护。
10. 小规模真实读写与真机播放验证通过后，再分批迁移；不以自动测试形式替代真实可用性，也不做无必要的大型重构。

当前代码的具体接入点与缺口：

- `worker/src/private-assets.js` 在存在`SPEAKING_ASSETS`时用其对象接口，否则把`PRACTICE_MEDIA` KV包装为对象接口；当前包装每资产限20MiB。
- `worker/src/practice-media.js` 已预留`PRACTICE_R2`，但一旦绑定即优先只读R2，没有旧KV逐资产回退。只加绑定会让老资产不可读。
- `worker/src/pronunciation.js` 的短点读仍直接走D1 BLOB，需单独适配。
- 正文章节依然按KV字符串读取，不能以口语存储适配已存在而宣称所有文件层已统一。
- 当前练习音频上传也有20MiB等本项目限制；服务商允许更大文件不代表现有上传接口直接支持。
- 当前若对长音频整个`arrayBuffer()`后再切Range，内存和重复上游下载会增加；选择新后端时应核实其范围读取能力。

## 14. 架构审计中与本研究有关的意见

用户要求核实真实功能缺陷，不把“不够正规”当问题。

- 题目科目排序一侧缺reading、CSS边框变量等真实小问题此前已修复；不能重复以旧版本报告宣称仍坏。
- 全部历史来源快照增长是真实潜在问题，但当前只是元数据，不等于每天把全部历史教材正文送入模型。可以共享版本化清单或分层检索，保留第一章至今的可用范围。
- 长期learner model、usage曝光/回忆/主动产出、自动复习是未来产品候选，不是已经完成的数据库需求。研究可为扩展留位置，不擅自加入新每日任务。
- 微缩全部题型的自然性需要真实答题与生成结果验证，数据库容量不能证明考试测量有效。
- 正式内容没有30天或1年的持续使用统计，长期增长区间应明确假设。
- 用户已明确不建设自动跨日充值等待监测；只保留材料、停止新收费、由用户明确恢复。
- 测试、正式日课、雅思和临时页独立；任何迁移样本不应标记VIX或制造正式学习数据。

## 15. 建议外部研究回答的问题

本节是研究目标，不预设最终胜者。允许提出更合适的正常用途服务，或否定已有排序，但应给出具体事实。

1. **最低改动方案**：保留D1与Worker，只替换媒体/原返回文件层，哪种服务最好？
2. **全量长期保存方案**：按1年、3年、5年，以低/中/高使用量估算存量、备份、读取和费用；分别包含与不包含嵌入音频请求副本。
3. **严格免费大容量方案**：OCI、GitHub分仓、HF等正常使用是否成立？实际容量、流量、权限、闲置、删库/停用、付款和恢复条件是什么？
4. **低价托管方案**：R2、B2、COS等费用多少，与自管方案相比是否节省足够费用？不要仅按免费GB排序。
5. **关系数据库是否需要迁移**：当前不到1MB、媒体迁出后的增长下，是否有真实必要？若要迁，Turso、PG、NoSQL各需改哪些现有语义？
6. **支付实际可达性**：区分支持卡组织、支持借记卡、本人已绑卡、学生免卡、免费起步和超额付费，不用笼统“支持中国用户”代替。
7. **iPhone实际体验**：私有音频首播、复播、Range、网络限制、鉴权与离线缓存如何保证？
8. **可靠性与独立备份**：数据持久性、跨账户副本、恢复时间、迁移退出和不重复生成如何实现？
9. **共享额度**：新仓/新库/新namespace是否增加真正账户额度？轮询、日志、逐片段存储是否仍会触限？
10. **证据版本保真**：删除、修订、去重和缓存如何保持旧chapter、question、attempt、call与反馈可回查？

希望输出一张统一候选属性表、不同保留策略的经济比较、待实测事项，以及可渐进实施的首选与备选。无需增加形式化测试体系、公众SaaS架构或已淘汰的功能。
