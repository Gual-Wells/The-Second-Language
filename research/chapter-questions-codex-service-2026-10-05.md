# 章节答疑服务：接入研究与收尾工作

日期：2026-10-05，北京时间。核查工程基线 `f3ec4ba9c77b3d05f5a12f4fb636d8bf8b2fb509`。

这是接入建议，不是已经启用的运行协议。没有修改生产后端、PWA、计划任务、VIX 或休息状态。用户提供的交互与全文方案是目标参考，技术实现以核查结果为准。

## 1. 结论

可以实现。采用 **本章对话 + 固定版本全文 + D1 待办 + 本机轻量检查 + Codex CLI 回答 + 后端保存 + PWA 未读提示**。

本项目是私人教材阅读器，一个问题通常只依赖一章。整章作为工作材料合理，没有必要先建立向量检索、逐句选区、额外题目索引或另一个付费回答模型。全文应由后端按章节版本取得；手机提交问题和版本身份即可，不必每次上传整章。

模型处理的是整章上下文，存储层保存的是问题与既有章节的关系。这既满足全文答疑，也避免重复保存教材正文。

## 3. 用户交互

入口设在章节标题区域上沿，使用紧凑的对话图形与“答疑”文字，保持现有蓝灰边框和按钮质感。它不占用第三部分的标记/译文工具栏，也不遮盖正文或改变点词、点句操作。

打开后是一个普通对话窗口：顶部当前章节与关闭按钮，中间消息列表，底部输入框与发送按钮。自动关联当前章，用户可以直接引用词、句或描述困惑。无需用户选义项编码、粘贴整章、配置模型或选择分析类别。

默认进入当前章的对话，窗口内可以回看其他章节的历史答疑。切换章节时保留各章草稿；退出窗口时保留正文位置。旧版本对话继续绑定旧版本，界面只需显示章节日期及必要的“原版”提示。

新回复到达后，入口显示一个小红点。自己发送问题、排队状态或余额记录更新不产生答疑红点。打开窗口不能直接把所有历史回复标为已读，应只确认实际显示的回复；其他章节仍有未读时入口保留红点。

等待状态只显示“等待处理”“正在回答”等自然文案。发送成功后可以关闭 PWA；回答保存在后端，重新进入仍能看到。前台刷新和恢复到前台时更新状态，不依赖 iOS 长时间后台轮询。此设计首先提供应用内红点，不把系统通知作为读取答案的前置条件。

## 4. 一次提问如何运行

1. PWA 提交当前章 ID、digest、问题、对话 ID 与一次发送标识。后端核对本人登录与章节版本，保存消息和待办；网络重试不会插入两个问题。
2. 本机普通程序约每 60 秒查询一个小型待办接口。无待办时结束本次检查，不启动模型，不写 KV，也不把空检查逐次写进 D1。
3. 有待办时领取问题，下载该 digest 的完整 Markdown 和本次追问需要的既有对话，存入独立工作目录。全文哈希必须与绑定版本相符；正文缺失时报告读取故障，不能改读最新版本冒充原文。
4. 启动 Codex，明确本章全文、用户问题和对话分别是什么。引用文本作为分析材料，不作为执行指令。直接理解定位、解释用法、辨析翻译和上下文，必要时回读教材资料。
5. 最终输出正文 Markdown，另有很少的稳定交接字段。Schema 用于成功落库与可选来源链接，不限制解释的段落、长度、例子数量或教学判断。
6. 普通发布程序检查结果格式并上传；后端按领取令牌一次性写入回答和回复序号。先保存本地完整回答再上传，上传失败时重传同一回答，不重新调用模型付出第二份生成消耗。
7. 回答完成后按 `BALANCES.md` 处理任务末尾额度快照。余额查询暂时失败不撤回已经成功保存的回答。
8. PWA 下一次状态检查或打开时显示回复与红点；阅读确认写入本人已读位置。

问题和追问按同一对话的先后次序回答。多次空检查不能领取同一问题启动多个 Codex。已领取的执行使用租约及少量心跳，超时先检查本地成果，再决定如何恢复；不把未知进程结果直接当成未生成。

提问不是改稿申请。回答本身不修改章节、词表标签、音频、雅思题目或推荐权重；如果用户确实要求修改，走相应已有任务通路。

## 5. 整章全文的专业判断

用户提出全文材料的目的合理：让解释理解文章语境，降低用户操作和模型定位的注意力成本。保留该目的，但采用服务端读取既有固定版本，减少传输与重复存储。

必须区分“文本文件体积不大”和“模型上下文没有成本”。40 主词的完整义项、词族、例句与覆盖全文可能很长；每次回答读取全文仍消耗 Codex 额度。运行前需要根据真实章节体量确认载体可完整处理，不承诺无限上下文。

本机保存全文文件便于回读，不能据此声称模型已经看过所有内容。答疑协议应要求理解相关词条、例句和文章前后文，涉及全章的问题须完整阅读所需部分；超长时分段回读全文，不静默删去后半章或只提供未经核实的摘要。

同一章的对话可连续追问，继续问题必须带上相关前文。长年历史永久保存，但一章的问题不用携带全部章节和其他对话。真正超长的单一对话可以另起讨论并保留历史导航，不让静默截断造成错误回答。

临时页的答疑扩展需要单独明确来源过期行为，不能借对话快照绕过已有 48 小时销毁约定。本阶段优先正式章节答疑。

## 6. 本机与成本

建议增加一个答疑专用的轻量检查入口，复用现有配置、认证、请求封装与 CLI 定位；不把目前每 30 分钟的雅思调度强行当作实时答疑。

检查程序可以由 Windows 计划任务在登录时启动并自动恢复，保持单实例。它不是持续运行的 Codex 模型会话：只有领到问题才启动 CLI。每次答疑有独立目录；模型只需要读材料和写回答，生产发布凭证由普通上传程序持有，不需要复制日课的宽权限配置。

同一时间最多一个答疑生成，避免多个追问抢先返回。与日课、雅思使用独立材料目录，可按本机与订阅实际并发能力调整；如果已有长作业或额度限制妨碍启动，显示排队，不承诺任何时候立即回答。初始方案不需要重构所有项目任务为一个总调度器。

| 消耗 | 解释 |
| --- | --- |
| 空队列检查 | 不调用 Codex，不调用 OpenRouter、Whisper 或腾讯；有 Cloudflare 请求及 D1 查询消耗 |
| 答疑生成 | 消耗现有 Codex 载体额度；不是免费推理 |
| 语音服务 | 纯文本答疑不需要声音分析或 TTS；额外点读仍沿用已有按需缓存 |
| 永久文件 | 对话、完整回答与必要过程资料，体量远小于原声与听力音频 |

按一分钟一次、24 小时不间断运行，检查器约 1,440 请求/日，占当前 Workers Free 100,000 请求/日额度的 1.44%。待办按状态与时间索引查询，避免扫描全历史；空检查不更新最后检查时间、不记录一次操作一条日志。D1 当前免费额度为 500 万读取行/日、10 万写入行/日，查询行数仍需以实际返回的 meta 统计验证。[Workers 限额](https://developers.cloudflare.com/workers/platform/limits/)、[D1 计费单位与额度](https://developers.cloudflare.com/d1/platform/pricing/)

这些只是答疑新增负荷的估算，不能替代整个 Cloudflare 账户其他项目的实际用量检查。之前触限是批量 KV 写入，答疑不采用那条通路。

## 7. 数据分配

D1 保存对话、消息、待办、领取状态、未读位置和来源版本关系。章节全文复用现有正式版本，OneDrive 接入后仍通过同一个章节读取接口取得。近期问答正文放 D1 便于简单读取，历史对话可按整段对话导出 OneDrive，保留目录与原件指针；不按每句话建立云文件。

不需要新建一个向量库，也没有理由只为低频文本答疑购买第二套数据库。归档不会删除永久原件、断开来源链接或清空用户记录。
