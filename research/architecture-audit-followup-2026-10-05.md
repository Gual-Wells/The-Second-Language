## 结论

确有值得现在补齐的运行和数据关联边界；没有发现必须更换整套架构的证据。现有章节版本、题目/答卷身份、独立练习数据库及媒体适配层能够承接这些修补。

不能把“有幂等发布和中间文档”直接等同于“跨日自动恢复与本机故障恢复已经闭合”，也不能把“后台固定了来源版本”直接等同于“读者跳转能打开该固定版本”。这两处需要沿完整通路补齐。

## 1. 可复现：练习索引混淆了来源范围与实际关联

位置：`worker/src/practice.js:59-84`；实际界面使用章节筛选，见 `web/practice.js:33-38`。

听力、阅读的章节筛选检查 `practice_sources`。发布时，该表写入申请时全部允许使用的历史章节（`practice.js:194`），不是实际被该篇材料采用的章节。实际篇章关联保存在 `links_json`。

因此，当练习允许使用 A、B 两章，某篇材料实际只关联 B，按 A 检索仍返回该篇所有题。随着历史范围扩大，按旧章筛选可能越来越接近“返回大量后来练习”，降低索引的实际用途。

写作、口语的章节条件与用法条件是两个独立 `EXISTS`。如果题目关联 A#U002 和 B#U001，按 A + U001 搜索也会返回它；这是章节内编码未按复合身份匹配。听力、阅读后置的 useId 筛选也没有和章节条件配成同一关联。

本机 `.cache/architecture-review-check.mjs` 调用真实 `practiceRoute`，应用全部实际 practice migrations；结果：

| 查询 | 应返回 | 实际返回 |
|---|---|---|
| A 章，听力 | 空 | 只关联 B 的听力题 |
| A 章，阅读 | 空 | 只关联 B 的阅读题 |
| A#U001，写作 | 空 | 关联 A#U002 / B#U001 的写作题 |
| B 章，听力 | B 的题 | B 的题 |
| A#U002，写作 | 相应写作题 | 相应写作题 |

建议：保留完整历史资格清单；题目索引根据实际 links 检索，章节和 USE 在同一关联中匹配。听力、阅读当前 links 是篇章级，索引应明确沿篇章关联查找，不能冒称已经有逐题语义关联。若将来确有逐题需求，可增加可选链接字段，无须重做现有题库。

## 2. 静态确认：跨日续作尚无确定性选择入口

位置：`scripts/run-daily.ps1:17-46`、`protocol/DAILY_RUN.md:3-17,33-35`、`AGENTS.md:3`。

定时入口每次取今天的北京日期，领取今天控制，再要求 Codex 完成今天四十词。未完成时允许留下 resume.md，并以进程正常退出结束。入口没有枚举旧的未发布运行，也没有以章节完成状态决定是否继续唤醒。

现有协议可以让模型继续已知的同一运行，但没有稳定的跨日旧任务选择规则。不能据此断言过去已经漏课；能确认的是：旧课自动收尾目前依赖额外判断或手动介入。

这在 VIX 已标记而正文未发布时更重要：旧词会退出下一次推荐池，因此“再选今天四十词”不能替代完成旧章节。

建议：增加待完成运行查询/选择与明确的日期交接。休息仍先按当天控制结束整个日课任务；非休息日显式识别旧运行，保持其原选词与原目标日期，完成或保留明确待办。旧任务和当天任务的先后处理应写清楚，不能悄悄把旧课改日期。正常 CLI 退出应区分“课程已发布”与“中间文档已保存”。

### 与此相关的持久化缺口

`work/runs/` 被 `.gitignore` 排除；这合理地保护了内部材料，但正式选词、主词/派生关系和草稿主要在本机。后端 `daily_runs` 只保存 selection digest、VIX commit、chapter digest 等字段（`worker/migrations/0001_core.sql:29-33`，`worker/src/index.js:98-115`），不能从摘要恢复原选词结构。

本机目录正常保留时可以续作；若磁盘资料丢失或更换机器，远端 VIX 日期标签只保留词条集合，未必足以恢复当时哪四十个是主词及其词族分组。因此“不可变 pin”并不等于“已有完整恢复材料”。

建议：至少给选词清单和发布待办一个私有持久副本，保存 runId、原日期、主词/词族、输入 pin 和标记 commit。重要草稿可在少数交接点备份，仍允许模型自由建立中间文档，不要求每次编辑上传或把工作文档公开。标记顺序继续遵循用户要求：完整确定推荐后标记，随后完成建设。

## 3. 静态确认：练习固定版本与读者跳转版本未闭合

固定来源已实现：申请保存 digest，发布者可通过 `/api/practice/publisher/sources/<chapterId>/<digest>` 读历史正文。

但 `web/practice.js:104`、`web/listening.js:36`、`web/reading.js:9` 的来源按钮只传 chapterId/useId；`web/app.js:449` 再调用普通 openChapter。普通 `/api/chapters/<id>` 始终取最新 published digest（`worker/src/index.js:213-222`）。

后果：章节修订后，旧练习的后台证据仍正确固定，读者点击来源却看见后来版本。即便编码保留，文本也可能改变；编码若不再存在，定位失效。现阶段这是具备明确触发条件的功能缺口，不是已观察到大量错误导航。

相关缺口：单章响应没有返回实际 digest，前端优先从此前加载的章节清单补 digest（`app.js:327`）。清单与正文跨版本更新时，阅读位置可能绑定到错误摘要。

建议：来源跳转携带申请时 digest，读者正文接口支持读取该版本并返回实际 digest。普通日历继续打开最新版本。旧版显示、位置身份和当前学习进度要明确区分，无须更换章节存储。

## 4. 容量风险：不可替代的学习资料与可再生音频缓存仍需分开管理

当前 `worker/wrangler.jsonc` 绑定 CHAPTERS、PRACTICE_MEDIA 两个 KV，没有 R2；`worker/src/private-assets.js` 将口语私有资产适配到 PRACTICE_MEDIA。原声、WAV 和多模型返回保真保留。听力/考官音频也通过媒体适配层保存。

独立 KV namespace 可以隔开键，不能隔开账户免费额度。Cloudflare 官方免费 KV：每天一千次写入、账户一 GB 存储。此前实验已经触发账户写额度；测试改为本机/静态产物的现行措施有实际价值。[官方 KV 限额](https://developers.cloudflare.com/kv/platform/limits/)

新点读已改为 D1 BLOB，减轻 KV 写入；但 pronunciation_audio 与真实答卷共用 PRACTICE_DB，单段上限一 MiB，却没有总容量/淘汰策略。免费 D1 单库上限五百 MB，点读缓存累积可能挤压答卷空间。具体到达时间取决于真实点击和音频大小，不能假称已经快满。[官方 D1 限额](https://developers.cloudflare.com/d1/platform/limits/)

建议：原声、完整返回与正式听力材料使用适合长期媒体的私有对象存储；短点读采用明确的总容量和清理规则。缓存可再生成，但删除应保留必要调用/收费状态，尤其不能通过清缓存把 outcome_unknown 变成自动重付。容量检查不能变成删除真实答卷或原声的理由。

已有 `PRACTICE_R2` / `SPEAKING_ASSETS` 适配入口，因此可以局部接入；迁移时保留旧 KV 对象的读取兼容，避免索引切换后旧资料失联。

附带但未复现的边界风险：允许十分钟 PCM16 WAV，约十九点二 MB，base64 约二十五点六 MB；后台多路并发序列化完整请求会扩大内存占用。不能仅凭体积断言线上内存溢出。若后续实际允许这种长答，应核对部署环境上限并控制并发或使用供应商支持的等价完整音频传输，不能剪掉学员原话。

## 5. 可复现：阅读位置只保留九十个章节版本/部分记录

位置：`web/app.js:166-175`。

saveReadingPosition 超过九十个 key 会删除前面的记录。三部分各一个位置，因此约三十个章节全部读过后，旧章位置会逐步丢失；临时页和修订版本也占名额。这与长期持久化各部分位置的要求有差距。实际阈值是九十个 key，不能简化成必定第三十一天丢失。

本机诊断读取真实 saveReadingPosition 函数：第九十一个记录加入后，最早记录不存在，新记录仍在。保存时更新旧 key 也不会重排 Object.keys，这不是按最近使用淘汰。

建议：位置数据体积很小，可长期保存正式章节位置；临时页位置可按 TTL 清理。不要让正式章节与临时页共享任意小的固定配额。跨设备同步是否需要是另一项产品选择，不由此报告擅自增加。

## 6. 小型功能问题：搜索字符检查不符合 D1 的字节限额

位置：`worker/src/practice.js:63-78`。

接口允许一百字符，实际使用 `%term%` 的 LIKE。D1 对 LIKE/GLOB pattern 的限制是五十字节，而不是五十 Unicode 字符。四十九个 ASCII 字符加两端百分号已有五十一字节，十七个汉字加通配符也超过限制。

按官方限制设置本机 SQLite 的 SQLITE_LIMIT_LIKE_PATTERN_LENGTH=50 后，同样模式触发 `LIKE or GLOB pattern too complex`。这是平台边界的本机模拟，没有调用线上搜索来制造错误。建议使用适合任意关键词长度的字面包含检索，或明确按 UTF-8 字节校验，避免合法界面输入触发后端错误。[官方 D1 限额](https://developers.cloudflare.com/d1/platform/limits/)

## 建议处理顺序

1. 修正实际来源/章节内用法索引与固定版本跳转，避免旧课和旧练习数据增加后产生错误关联。
2. 把跨日待办选择与私有恢复清单接上日课通路，保证已标记词最终有对应课程。
3. 为音频存储与缓存设置容量边界，并保留现有对象读取兼容。
4. 修复位置保存上限和搜索限额；修正口语当前说明及检查的迁移入口。
5. 真实学习后再决定是否需要 usage 学习事件或自动复习；不是本次架构修补的前置条件。

这些工作主要涉及少量查询、运行选择、版本参数、恢复字段及存储配置，不要求更换 PWA、推翻课程协议、缩小历史学习范围或改写整套口语采集。
