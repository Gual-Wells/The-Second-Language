# 第二语言：D1 长期容量有界方案

日期：2026-10-06。状态：研究设计，未修改生产 schema、读写路由、存储协议或清理任何正式数据。既有 OneDrive 授权、两份 D1 和章节预下载继续运行。

## 1. 结论与目标

推荐保留现有两份免费 D1，把它们改为**有容量上限的在线状态库及近期索引**；全部永久内容、完整关系、声音生成身份与历史目录由 OneDrive 文件及版本化清单承担。不是增加更多永久 D1 分片，也不是把全部关系压缩成一个数据库 BLOB。

这个方案的关键是：历史增加时，永久文件库增加；D1 使用量在明确的行数、行大小和物理容量门槛内轮换。正常规划每库控制在 100 MB 以下，200 MB 时停止接收会新增积压的工作，给已有任务和恢复留足余量，不等到 500 MB 才维护。

“几乎不会触及 500 MB”成立的条件是所有写入通路遵守容量边界、迁出验证和入口控制；它不等于免费账户每日读写额度绝不会耗尽，也不保证 Microsoft 账户、网络或订阅永不故障。长期异常不能一边无限接收数据、一边保证有限在线存储不增长：此时保留数据并明确停止接收新任务。

当前规模仍很小，适合在增长之前逐步完成。2026-10-06T03:01:42Z 管理接口只读核实：主库 file_size=708,608 字节，练习库 327,680 字节。先前已验证的恢复副本有主库 24 张业务表/1,245 行、练习库 22 张业务表/11 行；恢复副本与实时库不是同一时间截点。

官方边界：免费每库 500 MB、账户合计 5 GB、最多 10 库；每天 500 万行读取和 10 万行写入由账户共享。两种额度必须分别管理。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)、[D1 计量](https://developers.cloudflare.com/d1/platform/pricing/)

## 3. 各层职责

### 3.1 D1：小状态、入口、领取控制

保留：身份验证、当前设置、章节入口、近期练习入口、阅读进度、红点摘要、正在处理的任务、领取锁、收费结果未知的保护状态、待归档的少量引用、额度汇总和有限定位缓存。

从新写入起，大段输入、答卷、模型错误原文和生成返回先变成永久文件引用，不用“先全部塞 D1，以后再想办法归档”。UTF-8 字节上限与记录数量都校验；超长合法内容移入文件，不能截断内容凑大小。

### 3.2 OneDrive：全部永久内容及其关系

保存：章节所有版本；试卷和隐藏参考答案；每次答卷、录音、模型返回、批改、答疑；生成描述及结果状态；章节声音关联、角色音色、历史版本；全局目录和恢复快照。

资料以章节、套卷、一次作答、会话为单位组织。OneDrive 不运行 SQL；后端读取文件并沿现有业务逻辑生成产品响应。本机 Codex 同样可读取完整资料，不把它变成只能最近几章可用的项目。

### 3.3 缓存：可替换的副本

设备已有 CacheStorage 和 Worker 可失效缓存用于清单/音频加速。D1 只缓存近期的小定位信息，不缓存整个压缩清单。新方案不增加 KV 每词写入；正常开章仍取得整章正文、索引及已有音频包，保持用户已有的自动下载开关。

## 4. 永久目录如何脱离 D1

采用两类普通清单，避免复杂通用检索引擎。

1. **业务清单**：一章、一套试卷、一次作答、一段会话有独立版本化清单。包含完整自然 ID、版本、关系、文件摘要、位置、包内偏移和生成描述。未变化资料复用，不每次复制所有历史。
2. **按键查询目录**：用原逻辑键/生成 ID 的完整 SHA-256 前三个十六进制字符，直接定位 4,096 个可能的目录分组；只创建实际使用的组。分组清单放 OneDrive，包含当前定位和历史清单指针。D1 不存其中每条资产记录。

分组只是文件名计算，不需要另一个索引数据库。分组头可通过应用目录相对路径直接读取，避免列举整个云盘。微软支持相对路径和 itemId 两种寻址；下载地址动态获取，只在后端使用。[Graph 寻址](https://learn.microsoft.com/en-us/graph/onedrive-addressing-driveitems)

按偏上约 50 万份资产、每条目录数据 400 字节假设，完整当前目录约 200 MB、每组均值约 49 KB；这是容量算术，不是生产压缩实测。旧版本明细单独按业务清单保存，组头不能不断塞入全部旧版本。单个目录解压后上限暂设 512 KiB；超出时按下一位摘要拆该组，不重新分配全部资产，不把大文件解析负担转给每次 Worker 请求。实际 CPU 和延迟必须在试点中验证。

不可变文件仍按完整摘要定位。当前永久文件基座的摘要验证、OneDrive itemId、已有逻辑 ID 和旧 URL 不被迁移重写；新目录增加定位方式，后端继续支持旧链接。32 字节二进制摘要适合 D1 内部，但对外 ID 保持现有表示。

目录由一个归档写入者按批次更新，复用当前本机归档互斥，而不是点击一次就同时改全局总目录。不可变版本先上传并回读，再发布小型组头。失效写入者不得覆盖新头：实现时需要领取版本与条件写入，并验证所选 Graph 操作的 ETag 语义；不能只靠本机锁或假定任意 PUT 都支持可靠 CAS。官方上传会话提供 if-match/412 能力，但具体小文件发布路径尚需试点。[条件上传](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0)

## 5. 新数据提交与异常状态

一般资料：先取得有界在线槽位 → 上传永久内容和操作收据并回读 → 记录小引用 → 告知保存成功 → 归档服务把收据合入业务清单和按键目录 → 核对包含关系后轮换 SQL 副本。

操作收据保存本次自然 ID、关系、完整摘要、原字节/文件引用和状态。它保证目录暂未合并或本机暂离线时，新数据仍能恢复；不能只把关键的新位置留在等待归档的 D1 中。收据可批量归并进永久块，保留全部语义和所需原字节后才处理冗余物理副本，不删除最后原件。

收费调用：领取生成 ID → 核对永久目录及未合并收据 → 确认无既有成功结果或未知结果 → 保存调用意图 → 调用供应商 → 永久保存结果、描述和收据 → 返回状态。空缓存不代表没生成过；Graph 的 401、429、5xx、网络失败和校验失败不能当作“资产不存在”。即使是 404，也要核对目录代次与尚未合并的状态后，才有资格判断确实未生成。

已成功结果复用；calling/outcome_unknown 等状态不按时间直接丢弃、不自动重新收费。异常可以转为永久的“需要处理”条目，同时保留在线摘要；占用达到队列上限时停止接收新工作。旧异常归档后仍必须参与生成身份查询，不能通过清除 SQL 状态绕过未知计费保护。

Graph 故障时，已有音频包和近期材料可用；新增数据使用有界应急空间，达到边界后明确告知未保存/暂不能申请。不能无限依赖 D1 音频 BLOB 回退。当前最大 1 MiB 点读 BLOB 回退需改为：预先保留有界容量，最多小量承接，优先转为持久收据；不能因文件库故障连续生成收费音频。[Graph 节流](https://learn.microsoft.com/en-us/graph/throttling)

## 6. D1 行数、字节及物理空间边界

下表是**每库**的初始设计预算，不是现有迁移后的实测，也不是用户内容数量限制。槽位用于在线轮换；所有历史仍在永久层。

| 在线类别 | 最大槽位 | 每条载荷上限 | 满额载荷 |
|---|---:|---:|---:|
| 入口、目录头、章节/近期试卷摘要 | 8,192 | 1,024 字节 | 8 MiB |
| 近期文件定位 | 16,384 | 384 字节 | 6 MiB |
| 工作状态和领取控制 | 2,048 | 4,096 字节 | 8 MiB |
| 应急待提交引用/小资料 | 512 | 8,192 字节 | 4 MiB |
| 近期额度/事件去重记录 | 4,096 | 256 字节 | 1 MiB |
| 设置和会话等控制记录 | 256 | 1,024 字节 | 0.25 MiB |

真实 schema 可拆不同业务表，但每一类必须共用预算，不能每新增一张表就重新领取同一份容量。标识、额外列、二级索引、分页和碎片另算。已核实的永久资料才可占用可轮换槽位；未完成任务不能被 LRU 覆盖。行数校验需要数据库约束/原子领取配合，不能仅先 count 后 insert。

数值保守且可调。长正文与答卷进入文件，缩小的是 SQL 载荷，不是限制用户输入为 4 KiB。异常详细信息保真归档，在线层只保留错误类别和引用。

### 本轮容量模型

执行 research/d1-bounded-capacity-model-2026-10-06.mjs：带主键、完整 32 字节唯一标识、状态时间索引，填满全部 31,488 槽位及载荷；之后三轮全量替换，混用最大/较小载荷，不 VACUUM。分配页峰值 **36,519,936 字节，约 36.52 MB/库**。槽位与载荷越界被拒绝，SQLite integrity_check=ok。

这是 SQLite 拟议 schema 的容量模型，不是 Cloudflare D1 性能或真实 schema 迁移验收。它证明在全部类别满额且不依赖压缩时，基础容量远小于 500 MB；为实际表、索引和碎片把目标放宽为 **每库 100 MB 以下**。最终实施还必须按真实 D1 file_size 验收，不能宣称模型已证明所有数据库都只有 36.52 MB。

### 物理门槛

- 正常目标：每库 <100 MB。
- 120 MB：检查实际类别占用、异常积压和索引增长，优先迁出已完成记录。
- 160 MB：停止扩大定位/历史展示缓存；未完成任务优先，已有内容继续可读。
- 200 MB：拒绝会新增积压的新任务/新收费生成，保留已有提交、完成与恢复工作所需余量，主动告知具体原因。
- 不把 500 MB 设为清理触发点，不自动购买容量或新建更多永久库。

管理 API file_size 与 query meta.size_after 作为物理观测；任务末尾和已有维护阶段记录，避免每次读音频做管理接口查询。原有归档读取预算继续有效；新维护还需统计写入及索引写入，分批在预算内运行。

删除记录可能只使 SQLite 页可复用，不能承诺 file_size 立即缩小。本轮模拟故意不 VACUUM。D1 实际可用的空间回收方式须按官方接口验证；如需重建，在低阈值阶段先验证完整导出/恢复，再建设替换库、核对与切换。账户余量和额外库名额先核实，不把未拥有的名额当保证。[SQLite 文件组织](https://www.sqlite.org/fileformat.html)、[D1 SQL 支持](https://developers.cloudflare.com/d1/sql-api/sql-statements/)

| 全历史雅思来源 | 仍为第一章至当前全部已发布章节，本章显著加权；以来源快照文件绑定版本，不裁剪为近期来源窗口 |

| 旧题重新作答 | 直接读取旧试卷版本，新建小型在线 attempt 引用；不把整套历史重新塞回 SQL |

| 答疑与红点 | 分页取得本章完整历史及对应章节摘要，已读游标可归档；全局有更新标记保留在线摘要 |
| 点词、点句、预下载 | Bella、现有切换按钮和整章已有音频包维持；默认预下载不等于预生成全部音频 |
| 停机与独立恢复 | 不要求本机在线才能读已封存资料；Microsoft-only 恢复包含新增文件目录和未合并收据 |

当前 practice.js 用多表 SQL JOIN、json_each、instr 和每题关系构造索引，因此不能只把旧表搬走就算完成。必须建设明确的归档读取适配，并核对上述产品功能。跨文件不再有 SQL 外键，应在封存时核对关系完整性；在线领取与状态提交继续使用 D1 的原子性，不宣称 Graph 与 D1 有跨系统事务。

检索页只保存必要的题目检索字段与引用；隐藏答案不混入初始前端查询响应。通用跨几十年全文检索可能比 SQL 更慢，应分页/渐进显示，这是本设计的真实取舍；本项目约 78 套/年，不需要引入另一家全文搜索服务。

## 8. 长期使用量对新方案的影响

沿用已确认的两个独立参数：每周平均 1.5 套，每套平均 1.5 次完整作答，即 78 套/年和 117 次完整作答/年；全部词库约 15,000–16,000 主词、375–400 章。

| 情景 | 永久侧增长 | D1 的变化 |
|---|---|---|
| 全部点读约 27.2 万份 | 清单、文件、关联和完整描述增长 | 最近定位缓存最多 16,384 条；生成身份在永久目录查，非逐份永久 SQL 行 |
| 密集约 38.4 万/压力约 49.6 万份 | 文件目录分组较大，按实际阈值拆分 | 目录头/在线槽位保持边界，不增加数十万关系行 |
| 10 年雅思约 780 套、1,170 次完整作答 | 完整试卷、原声与证据永久增加 | 旧题/答卷归档；近期入口与工作状态轮换 |
| 20 年约 1,560 套、2,340 次完整作答 | 年度清单和业务包继续增加 | 仍受相同槽位约束，不能直接乘 20 年计算在线全文容量 |
| 长期每天大量答疑、无限新版本 | 会话消息页、版本及索引增长 | 保留有限近期入口；目录和已读状态可归档，不维持无限 SQL 全文 |
| 本机长期关机、Graph 授权失效 | 已有永久资料维持，未封存资料停留在线/收据 | 有界积压达到阈值明确暂停新工作，不能无限自动接收 |

未把内容数或作答次数砍掉换容量。永久库的 1 TB、文件数、个人其他项目占用与订阅仍需另外管理，不把 D1 安全误写为整个项目存储无限。

## 9. 请求量、音频文件数量与备份

读取先查小的近期定位；未命中才取一个业务清单/按键分组，随后访问音频。仍按整章进行预下载，不按当前词与邻词做预测。一个普通请求不扫描全目录，不全历史 SQL 导出，不对每次点读更新 last_access_at。近期缓存命中不产生新的永久版本。

存储命中率及冷读取延迟需试点实测。免费 Worker 的 CPU、内存、外部请求与 D1 调用都有限制；目录解压字节限制、每轮调用拆分和验证必须一起验收，不能把 D1 的减少换成 Worker 触限。[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)

音频包可保留现有 8 MiB 分块。包内短音频按索引 Range 取出时，需核对 206、Content-Range、长度与成员摘要；供应商可能返回整包 200，应有受限兼容路径，不冒充成功的范围请求。压缩的是文本清单；不能把整个音频包做 gzip 后仍期待原 MP3 偏移有效。[Graph 下载与 Range](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0)

永久保存语义不要求把同字节的点读原件、章节包和备份副本永远重复存三份；但当前迁移不擅自删除旧原件。是否让已封存音频包承接唯一原件，应另做包级恢复与点读验证，再决定。仅迁目录已能解除 D1 容量增长，不将音频物理合并设为其前置门槛。

微软关于约 30 万项目及更高预览支持的提示属于同步/性能条件，不能直接当作个人 Graph API 总文件硬上限，也不能忽视几十万小文件的实际代价。目录分组和业务包避免另造一份永不合并的逐文件索引收据。[OneDrive 限制说明](https://support.microsoft.com/en-us/onedrive/restrictions-and-limitations-in-onedrive-and-sharepoint)

备份改为两份有界 D1 的快照 + 文件目录与新版本根引用 + 未合并收据。永久块按摘要复用，旧版本完整保留；不要每次快照重新复制所有历史清单。独立恢复能从 OneDrive 应用目录根取得目录和收据，重建在线入口。恢复索引按年度分页，避免它自身成为需要每次全量重写的无限 JSON。

## 10. 实施顺序与验收

这是研究方案，当前不开始清理生产数据，也不把文字方案自动升级成已生效协议。

1. **小规模接入目录和提交收据**：增加文件清单读写及有界近期缓存；旧表/旧读取兼容。先用既有六段 Bella 和一章、一套试卷验证，迁移不合成新音频。
2. **切断最大增长源**：storage 三张永久目录表、点读请求/关联改走永久目录。历史 SQL 记录只在清单、旧版读取、独立恢复与生成复用全部验证之后迁出。
3. **适配试卷、答卷和答疑**：先让正文从文件可读、新写入完整保存，再归档 SQL 详细内容。全历史题目搜索、隐藏答案、旧题重答、红点和 Codex 队列逐项验证。
4. **强制在线边界**：各类共用槽位/载荷预算、应急回退上限和物理阈值。验证并发槽位争用、未知收费状态不被淘汰、Graph 故障和本机离线时的明确拒绝行为。
5. **正式验收**：真实 D1 file_size、meta.rows_read/rows_written、Worker CPU/请求、iPhone 冷/热读取、完整目录缺失、旧版恢复、跨年检索。普通与偏上使用模型验证，不批量调用收费模型造几十万声音。

迁移先回读校验再切入口，再处理可恢复副本。修改现有外键依赖前要核对未完成任务；不能先删 parent 表再依靠文件希望 child 路由还能运行。容量模型只验证结构空间，不替代真实功能与迁移验收。

不新增数据库供应商、不增加固定订阅，也不引入全天在线 VM、独立搜索服务或复杂分布式数据库。主要工程工作是永久目录及业务文件读取适配，工作量实际存在；可以分阶段完成，而不是做一个通用多层映射框架再重写整个项目。

## 11. 取舍与不采用方案

- 单纯二进制摘要/字典编码：有收益，但长期记录仍无限累计，不足以独立解决问题。
- 所有 SQL 内容 gzip BLOB：妨碍检索、仍有行和索引增长，不能作为最终方案。
- 不断新增 D1 库：单库上限缓解，账户容量、配额与多库维护仍存在，不作为正常扩展路线。
- 定期删历史：违背永久保存；只轮换已验证有永久原件的在线副本。
- 只按天数保留：归档故障时会误删未完成内容；必须以已验证封存和容量为条件。
- 每次收费请求依赖缓存是否命中：会重复生成；必须查询永久生成身份和未合并状态。
- 一张巨大云盘总目录/每次全文读取：将容量问题换成延迟和 Worker 内存问题；使用普通业务单位和固定摘要分组。
- 全部关系库移到云盘同步 SQLite：OneDrive 不是远程事务数据库，不能通过下载/覆盖整个 sqlite 文件处理并发答卷。

最终推荐：**永久文件与清单持续增长；D1 在线数据可验证地轮换且有硬预算。压缩和短编号只作为辅助。** 这能让正常多年使用不再逼近 500 MB；异常情况下以停止新增长保护已存内容，真实成本是历史冷访问适配及少量等待，不是新增持续账单。
